# Build Checklist Phase 5.4 -- Design Verification Evidence

## Screen-size verification

Tested the real running UI (`ui/`, `npm run dev`) against the real running
backend (`services/api/main.py`) and real Firestore data, at two common
demo/presentation resolutions, via `ui/verify_screen_sizes.mjs`
(Playwright, headless Chromium):

- **1920x1080** -- standard presentation/projector resolution.
- **1366x768** -- a common smaller laptop resolution, chosen specifically
  to stress-test the design at a tighter width than the primary target.

Screenshots for both, Case Queue and Case Detail: `queue-1920x1080.png`,
`detail-1920x1080.png`, `queue-1366x768.png`, `detail-1366x768.png` (all in
this directory). No specific demo device/resolution was provided for this
task, so both were checked rather than guessing a single one.

At both resolutions: no horizontal page overflow (checked programmatically
via `document.documentElement.scrollWidth > window.innerWidth`, both
`false`), the three-zone Case Detail layout holds together, and the Case
Queue table remains fully legible.

## Genuine issue found and fixed

**Evidence value clipping at 1366x768.** `ExhibitCard`'s raw fact-value
rendering (e.g. `device_risk_signals`, a compact JSON array with no spaces)
had no `overflow-wrap`/`min-width: 0` handling. At 1920px the one hyphen in
an ISO timestamp happened to be enough of a break opportunity to keep it
inside its column; at 1366px the same value ran past the card edge and was
visibly clipped, cutting off part of a real evidence value
("...SEEN_ON_DIFFERENT" with `_ACCOUNT"}]` missing from view). This is a
legibility defect on real evidence data, not a cosmetic issue, so it was
fixed: `ExhibitCard.tsx`'s `dd` gained `min-w-0 break-words` (one Tailwind
utility change, no layout/visual redesign). Re-verified at 1366x768: the
same value now wraps to a third line and is fully visible. No other visual
change.

## "Outside pair of eyes" (Build Checklist 5.4)

The checklist item explicitly asks for a human, uncoached, cold read. No
human reviewer was available in this task. As an honest stand-in -- not a
substitute for the real thing -- a fresh general-purpose agent with **zero
prior context** about Sentinel, this codebase, or this conversation was
shown only the two 1920x1080 screenshots and asked to describe what it
understood, unprompted, in under 400 words. Full transcript of the request
and response is reproduced below verbatim.

**What it got right, unprompted:** correctly identified the product as a
fraud/risk-review console for a human analyst; correctly identified the
highest-priority queue row and why (risk band + robustness + flag count +
amount, not any single field); correctly understood the flagged case's
story within its own stated "10 seconds"; and -- the most important check
for this product specifically -- correctly identified on its own that
Gemini's panel is advisory and the Policy/Human panels are where the actual
recommendation and final action live, without being told to look for that
distinction.

**What it flagged, and what was done about each:**

1. *"Live counterfactual re-check is not available... Phase 5.1 API
   surface... Contracts §23.1"* reads like a leaked internal engineering
   note in a production analyst UI. **Fixed** -- this is a genuine
   communication defect (internal jargon in user-facing copy), not
   cosmetic polish. Reworded to "Live re-check is not available for this
   case yet. The estimate above is the fast-path result only." No change
   to what the panel does or means, no layout change.
2. The "Fragile" explanation and the risk-score bar's label were found
   subjectively unclear on first read. **Not changed** -- this is a
   copy/clarity preference, not a defect (the information is present and
   accurate); redesigning copy for clarity is exactly the "UI polish"
   this task was scoped not to do.
3. Large empty space below the 3-row queue table at 1920x1080.
   **Not changed** -- there are genuinely only 3 open cases in the real
   Firestore queue right now; the table is exactly as tall as real data
   makes it. Fabricating more rows to fill the screen would violate "use
   real data, do not fabricate."
4. Citation-chip affordance (button vs. label) not obviously
   distinguished. **Not changed** -- a real, minor interaction-clarity
   observation, but changing chip styling is a visual design change, out
   of scope for this task.
5. The "not scored" robustness state on the reasoning-failed queue row
   read as ambiguous (bug vs. intentional). **Not changed** -- this is
   the correct, honest representation of a case whose reasoning genuinely
   failed and was never scored; no fix needed.

### Full cold-read transcript

> **Prompt given to the fresh agent** (verbatim): "You are being shown two
> screenshots of a web application you have never seen before, with no
> other context or explanation... Read [queue-1920x1080.png,
> detail-1920x1080.png]... 1) What kind of application/tool do you think
> this is, and who is it for? 2) ...can you tell which item most needs
> attention, and why? 3) ...within about 10 seconds of looking, what do
> you understand about this specific case?... is there anything that
> looks like an automated recommendation versus something a human needs
> to decide? 4) Is there anything... confusing, ambiguous, hard to read...
> 5) Is there anything that looks broken, cut off, or visually wrong?"

> **Response** (verbatim): "Looks like a fraud/risk-review console for
> payment transactions — something a bank, fintech, or payments processor
> would use. The audience is a human fraud analyst who reviews cases an
> automated system has already flagged, sees the evidence and an
> AI-generated risk assessment, and makes a final call (approve, block,
> escalate). The "Gemini's assessment" label suggests an LLM is doing
> first-pass reasoning that a human then checks.
>
> The top row: $499.99 at "merch_demo_electronics_risky," tagged High
> risk, Fragile robustness, flagged for "New device," "Unusual location,"
> plus a "+1" (hidden third reason). It's the only High-risk row (others
> are Medium), has the most flags, and the highest dollar amount. That
> combination — red "High" badge plus multiple stacked reasons — is what
> jumps out; nothing else on the row (age, state) differentiates it since
> all three cases show "HUMAN REVIEW" and similar ages (52-56 min).
>
> This is that same $499.99 case, an electronics purchase on a
> device/account with signs of takeover: a device seen on a different,
> known-compromised account just 2 hours before this transaction, a
> merchant with no prior history for this customer and a rising
> fraud-report trend, and a ~1758km jump in location. The system's policy
> engine (P-002) already recommends "Escalate" based on risk_band=HIGH.
> Gemini's text write-up is explicitly labeled "Advisory, not a decision"
> — so that's the automated recommendation — while the actual "Human
> decision" panel at bottom right is empty/unchecked and awaiting a person
> to click Clear / Block & hold / Escalate to senior. So the automation
> stops at recommending; the human still has to act.
>
> Confusing/ambiguous bits: "Robustness: Fragile" with a tooltip-like
> explanation about "1 high-materiality factor... would flip this finding
> below the escalation threshold" is genuinely unclear without more
> context... The score bar ("Low / Medium / High" with "score 0.95") in
> the left rail isn't clearly labeled as to what it's a score *of*... "Live
> counterfactual re-check is not available: it requires a backend endpoint
> outside the current authorized Phase 5.1 API surface..." — this is an
> internal engineering/implementation note leaking into what looks like a
> production analyst UI. An analyst wouldn't know what "Phase 5.1 API
> surface" means, and it reads like a dev placeholder left in. The queue
> table's "Robustness" column shows "not scored" for one row with no
> styling difference explaining why — is that a gap, an error, or
> intentional?
>
> Anything broken/cut off? The queue screenshot is mostly empty — a huge
> expanse of dark background below the 3-row table with nothing in it,
> which reads as either an unfinished layout or a very inefficient use of
> a 1920x1080 screen. Also on the detail page, the reason chips at bottom
> ("Exhibit 01, Exhibit 04" etc.) look like clickable tags but their
> affordance (button vs. label) isn't obviously distinguished from plain
> text elsewhere on the page."

**Recommendation:** a real human "outside pair of eyes" check (the actual
checklist requirement) is still recommended before the live demo -- this
AI cold read is evidence that the design communicates its core story
correctly to an uncoached reader, not a replacement for a human doing the
same check.
